# Security Model

## Trust boundaries

The operator and deterministic runtime policy are trusted within their configured scope. Models, agent backends, papers, web content, repositories, datasets, tool output, and experiment code are untrusted. Provider credentials, SSH keys, GitHub tokens, host files, other workspaces, and production infrastructure are outside the agent boundary.

The operator token is a separate infrastructure credential. It authorizes the daemon API, the UI's server-to-daemon connection, and operator login; it is not a provider credential and must not be supplied to agents, model prompts, experiment processes, or browser JavaScript. The daemon removes both operator-credential variables from its environment after loading the token so subsequently launched workloads do not inherit them.

## Single-operator authentication

AutoResearch currently has one all-powerful operator identity. Exactly one of `AUTORESEARCH_OPERATOR_TOKEN` or `AUTORESEARCH_OPERATOR_TOKEN_FILE` must be configured for `researchd`, the NiceGUI UI, and every `researchctl` command that calls the API. Missing, duplicate, malformed, or unsafe credentials prevent startup or the CLI call. An inline environment token is supported, but an owner-only file is preferred because environment configuration is more easily exposed through process and deployment tooling.

Authentication is mandatory even on loopback. Loopback limits network reachability; it does not distinguish the operator from another local user, a compromised process, a container with access to the listener, or an accidentally forwarded local port. Those actors must not gain unauthenticated read access to research state or control over run lifecycle, chat directives, and finalization. Loopback and authentication are therefore complementary controls, not alternatives.

The token is generated by `researchctl auth generate --file PATH` from 32 cryptographically random bytes. Its canonical representation is 43 unpadded base64url characters. The generator writes a new mode-`0600` regular file with one trailing newline, prints only the path, and refuses to overwrite an existing file. Token loaders reject symbolic links, non-regular files, group/other permissions, and files not owned by the consuming process's effective UID. The Go daemon and CLI accept only mode `0400` or `0600`; deployments should use that intersection even though the UI's own parser is less restrictive. See `docs/configuration.md` for loading rules and per-service ownership requirements.

`researchctl init`, `researchctl validate`, and `researchctl auth generate` are local/offline operations and do not require the operator credential. This limited exception permits initial provisioning and configuration checking; it does not make daemon or UI startup optional-authenticated.

### API enforcement and the health exception

The Go API requires one `Authorization: Bearer TOKEN` header before routing or reading a request body. Bearer comparison hashes the candidate and configured values and compares fixed-length SHA-256 digests in constant time. Wrong, malformed, and duplicate credentials receive the same generic `401 Unauthorized`, with `WWW-Authenticate: Bearer` and `Cache-Control: no-store`.

The sole unauthenticated Go API route is exactly `GET /healthz`. A different method, `/healthz/`, a query string such as `/healthz?verbose=true`, `/metrics`, every `/api/v1/` route including SSE, and even unknown routes require authentication. The health response contains only `{"status":"ok"}` and exists for low-privilege liveness probes; it is not a readiness or research-data endpoint.

`researchctl` automatically loads the same token and sets the Bearer header for REST and SSE calls. It refuses HTTP redirects rather than forwarding the operator credential to a redirect destination. Use the final trusted API URL directly and use HTTPS for any non-loopback API path.

### UI authentication boundary

The UI also loads the operator token at startup, but uses it only in the Python backend to verify login and authenticate its proxy requests to `researchd`. A successful login creates an expiring server-side NiceGUI session containing authentication state and an absolute expiry, not the operator token. The browser receives a finite, signed, `HttpOnly` session cookie with `SameSite=Strict`; `Secure` is enabled when an HTTPS origin is configured. The cookie-signing secret is an independent random 256-bit value generated at each UI startup, neither derived from nor persisted with the operator token. Consequently, every UI restart invalidates existing browser sessions even if the operator token is unchanged.

The UI's public health probe is `GET /health`. `GET` and `POST /login`, the favicon, `/static/` assets, and a narrow set of versioned NiceGUI static/library/component/ESM assets are also public so the login page and framework can load. These exceptions do not expose research data. All application pages, runtime/internal proxy endpoints, SSE, private NiceGUI resources, and WebSockets require a valid session.

Exact Host and Origin allowlists apply before route authentication. Any supplied Origin must match; unsafe HTTP methods and every WebSocket additionally require an allowed Origin. This Origin check is the CSRF and cross-site WebSocket control and works with the Strict cookie. Non-loopback origins must use HTTPS. See `docs/configuration.md` and `docs/web-interface.md` for settings, throttling, and revocation behavior.

Logout, detected expiry, and session revocation clear authentication state, cancel that session's SSE streams, and disconnect its registered NiceGUI clients. Interactive callbacks recheck the active session, and SSE streams periodically reauthenticate rather than remaining authorized indefinitely after the initial request.

## Autonomy boundary

Before a run, the operator defines tools, filesystem roots, executors, network destinations, budgets, concurrency, remote resources, and publication policy. Routine permitted actions need no approval. Actions outside that boundary require explicit operator authorization or are rejected.

Operator authentication establishes that a request possesses the single operator credential; it does not expand a model's autonomy or convert chat into an authoritative directive. The structured runtime policy remains a separate authorization layer.

## Controls

- Mandatory single-operator authentication for daemon, UI, and API-using CLI commands, including loopback deployments.
- Strict tool schemas and role allowlists.
- Dedicated least-privilege provider credentials and secret redaction.
- OS-level workload isolation and resource limits, not prompt-based restrictions.
- Default-deny network and no host Docker socket in workloads.
- Per-agent workspaces and artifact checksums.
- Owner-only UID-matched token files, constant-time Bearer verification, and no credential forwarding across CLI redirects.
- Expiring server-side UI sessions, finite Strict cookies, exact Host/Origin allowlists, CSRF/WebSocket checks, throttled login, and active-stream/client revocation.
- Immutable audit events and emergency stop.

## Provisioning and rotation boundary

Compose gives the original file-backed secret only to a one-shot initializer. That initializer copies it into a private volume as UID `65532`, mode `0400`; only `researchd` and `ui` mount that volume read-only among long-running services. Other services, including model and agent transports, do not receive the operator token. With systemd or separate host services, either run all consumers and the CLI under the same UID or provision separate UID-owned copies containing the same token for each consumer. Group access is not a supported substitute.

Rotation replaces the token rather than adding a second accepted credential. Rerun the Compose initializer or replace every host/service copy, update CLI copies, and restart both `researchd` and the UI. The daemon then rejects old Bearer tokens; UI restart loads the new upstream token and generates a new session-signing secret, invalidating old UI sessions. There is no hot reload or overlap period. Exact commands are in `docs/deployment.md`.

Repository and Docker build ignore rules exclude environment files, token/secret/key patterns, private storage, and `.nicegui` state. Runtime secret mounts must never be replaced with `COPY`, committed environment files, inline YAML values, or image build arguments. See `docs/deployment.md` for the build exclusion requirements.

## Native Kimi boundary

The native `kimi web` service is a shared authenticated transport, not a shared agent context. Each agent has a separate KAP session and workspace, and the provider sends only new runtime messages rather than replaying the whole conversation. Runtime tool calls use a strict JSON envelope and are authorized in Go. Kimi built-in tools default to `manual`; `auto` and `yolo` are rejected because all sessions in the service currently share an OS identity and workspace volume. Pending native approvals or questions are errors, never automatic approvals.

A non-root relay exposes only `server.token` to the daemon with mode `0400`; the OAuth-bearing Kimi home remains private to the native service. This token authorizes the KAP transport, so it is still a sensitive credential and is never logged or included in configuration snapshots. It is distinct from `AUTORESEARCH_OPERATOR_TOKEN`: the former authorizes the daemon to the native provider transport, while the latter authorizes an operator to AutoResearch. Native provider OAuth is likewise not operator SSO.

A native session can retain provider-side history and compaction state. Runtime recovery uses durable structured research state and creates a fresh native session rather than assuming that a previous session is intact.

## Human directives

Chat is informational; directives are authoritative structured operations with operator identity, validation, and audit events. A model cannot promote a chat message into a policy change. Budget and executor changes require runtime validation and, when configured, separate confirmation. In the current single-operator model, “operator identity” means possession of the shared operator credential or its UI session, not a distinct per-user identity.

## Publication

The public repository contains only generic source, examples, and documentation. Research reports, datasets, experimental code, and logs remain private unless the operator explicitly exports and reviews them. Automated public pushes of research artifacts are prohibited.

## Limitations

There is no OIDC, OAuth-based operator login, RBAC, per-user delegation, read-only role, or per-user audit attribution yet. Every holder of the token has full operator control. Protect the token and every UI session accordingly.

No sandbox eliminates all kernel, supply-chain, side-channel, provider, or remote-host risk. Root on the host, compromise of the service UID, theft of a token or authenticated browser session, and a malicious TLS endpoint remain outside this mechanism's protection. Login throttling is bounded and per UI process, not a substitute for network rate limiting or denial-of-service protection. Health endpoints intentionally disclose liveness without authenticating the caller.

The runtime cannot prove that model-generated research is correct. Operators remain responsible for disclosure, licensing, source terms, credential rotation, HTTPS and proxy configuration, and independent scientific review.
